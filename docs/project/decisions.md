# Журнал ключевых решений

## D-001
Статус: принято

Решение: делаем локальный Android MVP до backend-реализации.

Причина: сначала нужно получить полезное и устойчивое приложение.

## D-002
Статус: принято

Решение: используем Kotlin, Compose, Material 3 и Room.

Причина: современный практичный стек для Android-приложения с локальным хранением.

## D-003
Статус: принято

Решение: архитектура `presentation -> domain -> data`.

Причина: достаточно для поддерживаемого MVP и будущего sync.

## D-004
Статус: принято

Решение: один питомец в MVP, но без захардкоженных данных.

Причина: соответствует реальной задаче и не мешает масштабированию.

## D-005
Статус: принято

Решение: категории типов событий фиксированные на первом этапе.

Причина: упрощает модель и UI без потери пользы.

## D-006
Статус: принято

Решение: monorepo с отдельными `android/`, `backend/`, `api/` и будущим `infra/`.

Причина: Android и backend должны развиваться независимо, но по явному контракту.

## D-007
Статус: принято

Решение: backend первого этапа на Kotlin, Ktor и PostgreSQL.

Причина: согласовано со стеком проекта и подходит под личный Ubuntu-сервер.

## D-008
Статус: принято

Решение: sync через local-first Android, серверные UUID, версии записей и cursor API.

Причина: достаточно просто для двух пользователей и одного питомца.

## D-009
Статус: принято

Решение: модель доступа — один текущий питомец в MVP, роли `OWNER` и `MEMBER`, invite flow; текущий продуктовый сценарий рассчитан на двух пользователей, но архитектура не должна завязываться на жесткий максимум два участника.

Причина: покрывает реальную задачу без сложной ACL и оставляет путь к расширению состава участников.

## D-010
Статус: принято

Решение: настройки локальных напоминаний не синхронизируются как общая сущность.

Причина: напоминания относятся к устройству и UX, а не к общей истории питомца.

## D-011
Статус: принято

Решение: Android Gradle root вынесен в `android/` отдельным структурным рефакторингом.

Причина: закрепляет границы клиента до добавления backend и API.

## D-012
Статус: принято

Решение: source of truth для backend API — TypeSpec в `api/`, OpenAPI производный.

Причина: снижает риск расхождения контракта.

## D-013
Статус: принято

Решение: backend skeleton с `GET /health`, конфигурацией и route-группами под контракт.

Причина: позволяет рано проверить запуск сервера и структуру проекта.

## D-014
Статус: принято

Решение: persistence foundation на PostgreSQL, Flyway и Exposed DSL.

Причина: реальная БД-основа для auth, pet access и invite flow.

## D-015
Статус: принято

Решение: auth foundation на `email + password`, JWT access token и opaque refresh token.

Причина: простая, но реальная авторизация.

## D-016
Статус: принято

Решение: invite flow через простой invite code, OWNER-only create, authorized accept.

Причина: покрывает shared access без multi-pet и сложной ACL.

## D-017
Статус: принято

Решение: доменные backend-таблицы `event_types`, `pet_events`, `weight_entries` сразу sync-ready.

Причина: готовит persistence foundation для `sync/bootstrap`.

## D-018
Статус: принято

Решение: server-side V1 считает все `event_types` пользовательскими, без флага системности.

Причина: проще для первой серверной итерации.

## D-019
Статус: принято

Решение: `sync/bootstrap` возвращает полный snapshot с soft-deleted записями и cursor `bootstrap:<epochMillis>`.

Причина: дает устойчивую точку первичной и аварийной синхронизации.

## D-020
Статус: принято

Решение: `sync/changes` строится на модели `(cursorTime, highWatermark]` по `updatedAt`.

Причина: простая incremental-синхронизация с tombstone-состояниями.

## D-021
Статус: принято

Решение: `sync/push` поддерживает `EVENT_TYPE`, `PET_EVENT`, `WEIGHT_ENTRY` и optimistic concurrency.

Причина: минимально достаточная server-side модель приема мутаций.

## D-022
Статус: принято

Решение: Android хранит `remoteId` рядом с локальным Room `id`, локальные мутации пишет в `sync_outbox` транзакционно.

Причина: сохраняет текущий UI/DAO-контур и готовит sync.

## D-023
Статус: принято

Решение: client-side read path вокруг remote data source, `sync_state` и транзакционного import/apply слоя.

Причина: понятная read-side интеграция без преждевременного merge.

## D-024
Статус: принято

Решение: client-side push path дренирует outbox, удаляет accepted, conflicts переводит в `FAILED`/`CONFLICT`.

Причина: первый рабочий end-to-end sync cycle.

## D-025
Статус: принято

Решение: app-level sync V1 вокруг `RunFullSyncUseCase` и ручного запуска из настроек.

Причина: реальная точка запуска sync без сложной state machine.

## D-026
Статус: принято

Решение: foreground-trigger через `MainActivity.onStart()` и `AppSyncRunner`.

Причина: естественный запуск sync без premature background orchestration.

## D-027
Статус: принято

Решение: sync-конфигурация вынесена из `sync_state` в DataStore-backed session/config store.

Причина: разделяет session/config и operational sync state.

## D-028
Статус: принято

Решение: background sync foundation на unique periodic `SyncWorker` через WorkManager.

Причина: безопасный фон без дублирования sync-логики.

## D-029
Статус: принято

Решение: client-side auth/session V1 вокруг backend auth endpoints и `SyncSessionStore`.

Причина: переводит sync из debug-only режима в пользовательский сценарий подключения.

## D-030
Статус: принято

Решение: conflict UX V1 через `sync_conflicts`, экран конфликтов и действия `принять серверную версию` / `повторить мои изменения`.

Причина: дает пользователю выход из `CONFLICT` без merge editor.

## D-031
Статус: принято

Решение: app-level entrypoint конфликтов на главном экране через мягкую карточку.

Причина: делает конфликты заметными без агрессивного global warning UI.

## D-032
Статус: принято

Решение: backend E2E smoke оформлен как `backend/e2e-smoke.mjs`; совместимые интеграционные расхождения чинятся сразу.

Причина: проверять живое поведение auth/invite/sync/conflict, а не только сборку.

## D-033
Статус: принято

Решение: Room migrations `3 -> 4`, `4 -> 5` идемпотентны; `5 -> 6` нормализует syncable-таблицы пересозданием.

Причина: реальные device logs показали `duplicate column name: requiresBootstrap` и schema mismatch `weight_entries`.

## D-034
Статус: принято

Решение: `SyncSessionStore` в DI-графе предоставляется как `@Singleton`.

Причина: иначе несколько DataStore на один файл дают crash `There are multiple DataStores active for the same file`.

## D-035
Статус: принято

Решение: dev backend слушает `0.0.0.0:8080`; Android smoke через Windows emulator выполняется через `adb reverse` и URL `http://127.0.0.1:8080`.

Причина: для Windows/WSL/Android emulator нужен стабильный IPv4 loopback и при необходимости `netsh portproxy`.

## D-036
Статус: принято

Решение: состояние `requiresBootstrap` в Android не чинится единственной destructive-кнопкой. UI должен явно предлагать два направления: `Отправить мои данные на сервер` и `Заменить данными с сервера`.

Причина: если сервер пустой, а на клиенте уже есть полезные локальные данные, full bootstrap с сервера уничтожит локальное состояние. Пользователь должен явно выбрать источник истины для первичной синхронизации.

## D-037
Статус: принято

Решение: выход из питомца является серверным `leave`, а не локальным `logout`. `MEMBER` может выйти напрямую. `OWNER` либо атомарно удаляет серверного питомца, если он единственный активный участник, либо атомарно передает ownership выбранному активному участнику и выходит.

Причина: владелец не должен оставлять питомца без владельца, а backend должен сохранять консистентность membership при будущем расширении списка участников.
